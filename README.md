# FormGen — 低代码与智能表单生成引擎

> 探索一种交互范式：**人类用自然语言描述需求，系统动态渲染出可直接使用的工具。**

零依赖，`node src/cli.js serve` 即可运行，不需要 `npm install`。

```bash
cd formgen

# 自然语言 → 表单，看它理解成了什么
node src/cli.js gen "做一个活动报名表：姓名、手机号、参加场次（上午/下午/全天）、参加人数、是否需要停车位，需要的话填车牌号"

# 教师大纲 → 组卷（含 LaTeX 公式）→ 可作答、可自动判分的考卷
node src/cli.js exam "高一数学期中试卷，满分150分，考试时间120分钟，包含选择题10道每题5分、填空题4道每题5分、解答题5道，覆盖函数、三角函数、数列" --text

# 启动微型平台：生成器 / 采集页 / 结果与导出
node src/cli.js serve
#   → http://127.0.0.1:4321/studio
```

## 一分钟看懂它做了什么

```
中文需求
   │
   ├─ 规则引擎（确定性、离线、可解释）──┐
   │                                    ├─→ FormSchema（纯 JSON）
   └─ 大模型（处理意图性表达）──────────┘         │
                                                  ├─→ 渲染：浏览器把它变成可填写的页面
                                                  ├─→ 校验：提交时按同一份 Schema 校验
                                                  ├─→ 存储：JSON 文件，可导出 CSV/JSON
                                                  └─→ 评分：考卷客观题自动判分 + 成绩分析
```

一份需求的完整生命周期：

```
$ node src/cli.js gen "帮我做一个员工入职信息收集表，包含姓名、手机号、身份证号、入职日期、部门（技术部/产品部/设计部），还要上传身份证照片"

员工入职信息收集表  [form]
1 个分组 · 6 个字段 · 2 个必填

  (默认分组)
    姓名          *   text
    手机号        *   tel
    身份证号          idcard
    入职日期          date
    部门             select (技术部/产品部/设计部)
    身份证照片         file
```

这几个类型不是猜的：`手机号 → tel`（内置 11 位校验）、`身份证号 → idcard`（内置 ISO 7064 校验位算法）、
`部门（技术部/…） → 下拉框并提取选项`、`上传身份证照片 → 文件`。

## 两个场景

### 一、教师大纲 → 含 LaTeX 公式的考卷

```bash
node src/cli.js exam "生成一份高一数学期中试卷，满分150分，考试时间120分钟，\
包含选择题10道每题5分、填空题4道每题5分、解答题5道，覆盖函数、三角函数、数列，难度中等偏难，公式用 LaTeX"
```

流水线：**需求 → 命题蓝图 → 约束组卷 → 可渲染/可评分 Schema**

```
命题蓝图
【高一数学期中试卷】数学 · 高一
总分 150 分 | 时长 120 分钟
知识点权重：函数 33.3%、三角函数 33.3%、数列 33.3%
题型结构：
  一、选择题：10 题 × 5 分 = 50 分
  二、填空题：4 题 × 5 分 = 20 分
  三、解答题：5 题 × 16 分 = 80 分
合计 150 分，与设定总分 150 分一致
配平调整：无（大纲分值本身已闭合）
```

三个关键点：

1. **用户明示的分值不会被改写。** 老师说了「选择题每题 5 分」，那就是硬约束；剩下没写分值的解答题去吸收余额
   （150 − 10×5 − 4×5 = 80，80 ÷ 5 = 每题 16 分）——这正是老师脑子里算的那笔账。
2. **实际总分精确等于计划总分。** 题库里每题自带的分值只是默认值，进入某道大题后就值该大题的 `scorePer`，
   所以不会出现「满分 150 的卷子实际 124 分」。
3. **同一 seed 可复现。** 对考试来说，可复现是硬要求。

公式走 **LaTeX → MathML**（`src/latex/mathml.js`，手写词法+递归下降解析器，无 `eval`，约 51KB，覆盖分式/根式/上下标/
大运算符/矩阵/分段函数/希腊字母/黑板体等常用子集）。输出浏览器原生 MathML，**离线可用、无 CDN 依赖**。
对畸形输入（`\frac{`、`{{{{`、超长嵌套）保证不抛异常，未知命令降级为可见字面量。

### 二、企业需求 → 全栈收集页面

在 `/studio` 里写一句需求 → 实时预览 → 一键发布 → 得到填写链接和结果页。

- 条件逻辑：「如果是素食，请填写具体说明」→ 自动生成 `visibleWhen` 表达式，**并自动补建缺失的字段**
- 计算字段：`compute: "round(price * quantity * 0.87, 2)"`
- 校验：必填、正则、范围、身份证校验位、选项合法性、跨字段规则（结束日期 ≥ 开始日期）
- 采集：草稿自动保存、进度条、服务端二次校验、CSV/JSON 导出（CSV 带 BOM，Excel 打开不乱码）

## 四个技术主张

### 1. 中间表示是唯一事实来源

自然语言被编译成 `FormSchema`（纯 JSON）。渲染器、校验器、导出器、评分器**只读这一份数据**。

没有「生成页面代码」这一步，所以不存在生成产物与需求漂移的问题：改需求就是改数据，
可 diff、可版本化、可回滚、可审计。

### 2. 前端与后端的校验是同一份代码

引擎是零依赖纯 ESM，服务端把 `src/` 原样挂在 `/engine/` 下：

```js
// public/runtime.js —— 浏览器里跑的
import { validateSubmission } from '/engine/core/validate.js';
```

浏览器 `import` 的就是服务端校验用的那个函数。**「前端过了后端不过」在结构上不可能发生**，
因为它们是同一个实现。这也是选择「不生成代码」的直接收益。

### 3. 双生成通道，而不是二选一

| | 规则引擎 | 大模型 |
|---|---|---|
| 定位 | 确定性、可解释、离线可用 | 处理规则覆盖不了的意图性表达 |
| 产出 | 每个字段为什么是下拉框、为什么必填，都能追溯到一条规则 | 更懂「问题要能让销售 30 秒内判断跟进优先级」这类需求 |
| 失败时 | 永远可用 | 自动降级到规则通道，并**如实带回失败原因** |

两条通道产出同一种 Schema，所以可以互相比较：

```bash
node src/cli.js gen "..." --mode compare
# 规则通道  ：6 字段 / 1 处逻辑
# 大模型通道：8 字段 / 3 处逻辑
# 仅大模型识别：客户等级、预计成交时间
# 结论：大模型补充了 2 个规则引擎未识别的字段；其中 2 个是规则词典没有覆盖的表达。
```

配置大模型通道（可选，不配也能完整运行）：

```bash
export DEEPSEEK_API_KEY=sk-...        # 或 OPENAI_API_KEY
export FORMGEN_MODEL=deepseek-chat    # 可选
export FORMGEN_BASE_URL=https://api.deepseek.com/v1   # 可选，任何 OpenAI 兼容端点
```

模型只被允许产出 FormSchema JSON，**不产出代码、不产出 HTML**；产出必须通过与规则通道完全相同的
`normalizeSchema` 校验；失败时把具体错误回灌给模型自修复一次，仍失败才降级。

### 4. 表达式引擎是「低代码」真正的落点

条件显示、计算字段、校验规则共用一种 DSL，用**手写词法+Pratt 解析器**求值，不使用 `eval`：

```
department == "技术部" && years >= 3
round(price * quantity * 0.87, 2)
饮食禁忌 == "素食"
age >= 18 且 姓名 != ""
```

安全约束：作用域只能读到显式传入的普通对象，`__proto__` / `constructor` / `prototype` 被拒绝；
解析或求值失败返回 `undefined` 而不抛错——表单逻辑写错不该让整个页面白屏。

中文可用：全角数字自动归一，`且/或/非` 与 `&&/||/!` 等价，**中文字段名可直接做标识符**
（`参会日期` 这样的 key 比 `f6` 有意义得多）。

## 目录结构

```
formgen/
├─ src/
│  ├─ core/           引擎内核（零 Node 依赖，服务端与浏览器共用）
│  │  ├─ schema.js      FormSchema 类型系统、中文别名归一、规范化
│  │  ├─ expr.js        表达式引擎（安全求值，无 eval）
│  │  ├─ validate.js    校验器 + 条件可见性 + 计算字段
│  │  └─ errors.js      带稳定错误码的 FormgenError
│  ├─ gen/            自然语言 → Schema
│  │  ├─ nlp.js         规则通道（中文语义词典 + 槽位填充）
│  │  ├─ llm.js         大模型通道（提示词契约 + 自修复 + 降级）
│  │  ├─ exam-intent.js 考卷需求 → 命题大纲
│  │  └─ index.js       通道编排与对比
│  ├─ exam/           考卷内核
│  │  ├─ blueprint.js   大纲 → 命题蓝图（含总分动态配平）
│  │  ├─ select.js      约束组卷（种子化随机 + 多轮重启）
│  │  ├─ bank.js        题库加载（.js / .json 均可）
│  │  └─ paper-schema.js 试卷 → FormSchema
│  ├─ latex/mathml.js  LaTeX → MathML
│  ├─ render/html.js   服务端 HTML 外壳（很薄：只渲染外壳与元信息）
│  ├─ server/          HTTP 服务 + JSON 存储
│  └─ cli.js           命令行
├─ public/            浏览器端（运行时 / 生成器 / 样式）
├─ banks/             题库（数据资产，替换题目不用改引擎）
└─ test/              158 个测试
```

## 界面

背景插画在 `public/bg.jpg`（`bg.png` 为原始素材，同一张图但大 6.8 倍）。
用固定定位的伪元素实现，而不是 `background-attachment: fixed`——后者在移动端掉帧，且无法单独叠一层遮罩。

插画中心是人物、左侧是密集的表格，直接垫在文字下读不了，所以上面叠了一层主题色遮罩。
强度由 `public/app.css` 里的一个变量控制：

```css
:root { --bg-scrim: 70%; }                    /* 调小 → 图更明显；调大 → 文字更清晰 */
@media (prefers-color-scheme: dark) { :root { --bg-scrim: 92%; } }
```

亮色主题能用较低的 70%，是因为图与底色都是高调浅色，压完仍是浅底、深色正文对比度足够；
深色主题必须压到 92%，否则浅色正文会糊在亮图上看不清。
承载正文的面板用 `--surface-veil`（94% 不透明）保证表单与卡片始终清晰，打印时背景自动隐藏。

## 已知局限（如实列出）

1. **规则通道依赖中文词典与句式。** 遇到没见过的表达会漏字段——但漏掉的会在「问题」里如实报告，不会假装成功。
2. **文件上传走 base64 内联**，单文件上限 2MB，没有分片与对象存储。
3. **存储是 JSON 文件**，适合演示与中小规模采集，不适合高并发写入。
4. **题库覆盖面有限。** 种子题库是高中数学 39 题。题库不足以支撑蓝图时，系统会给出缺口分析与补充建议，
   而不会假装组卷成功。
5. **主观题不自动判分。** `isCorrect()` 对解答/证明题返回 `null`（判不了 ≠ 判错），成绩分析里标为「待人工」。
6. **LaTeX 子集有边界。** 不支持 `\newcommand` 宏、`\label/\ref`、`\over`、真彩色、`\substack` 真堆叠；
   裸 `%` 不当注释（需写 `\%`）；`\int` 的上下限用上下限排版而非行内侧标。
7. **矩阵题、复杂排版**（图片题、多栏、双栏试卷）未实现。
8. **组卷未做跨卷去重**，同一题库多次组卷可能重复用题。

## 为什么不做「生成代码」

低代码平台常见的做法是生成一份页面代码。这里刻意不这么做。

代价是灵活性有上限——这套引擎表达不了任意 UI。收益是：

- **安全性**：模型产出的是受 Schema 约束的数据，不是可执行代码，注入面小得多
- **一致性**：预览与线上、前端与后端，跑的都是同一份实现
- **可审计**：一份 JSON 能被人读完，也能被 diff
- **可演进**：渲染器升级，所有历史表单一起受益

这个取舍是否值得，取决于你要做的是「表单引擎」还是「任意应用生成器」。
本项目赌的是前者——绝大多数收集类需求，其实不需要图灵完备。
